# postgres-mcp-ts

A TypeScript MCP (Model Context Protocol) server that exposes a PostgreSQL database to Claude and other MCP clients over HTTP. Claude can call 4 tools: `list_schemas`, `list_tables`, `describe_table`, and `query` (read-only SELECT only).

## Stack

- **HTTP framework**: Hono + `@hono/node-server`
- **MCP transport**: `@hono/mcp` (JSR) — Streamable HTTP (POST/GET/DELETE on `/mcp`)
- **MCP SDK**: `@modelcontextprotocol/sdk`
- **Database client**: `postgres.js` (not Prisma/Knex)
- **Validation**: Zod (env config + tool input schemas)
- **Build**: tsup → `dist/index.js`
- **Runtime**: Node.js v24+ (see `.nvmrc`)

## Project Structure

```
src/
  index.ts        # Hono server, /mcp route, session map, auth middleware
  config.ts       # Zod-validated env vars (fails fast on startup)
  db.ts           # Shared postgres.js connection pool
  mcp.ts          # MCP server factory, registers tools from tools/
  users.ts        # users table: create/list/rotate/activate/lookup-by-key
  tools/
    postgres.ts   # All 4 tool definitions (description, Zod schema, handler)
scripts/
  manage-users.ts # CLI to add/list/rotate/activate/remove MCP users
  smoke-test.ts   # HTTP integration tests (auth, routing, errors, tool calls)
  claude-test.sh  # End-to-end test via Claude CLI
  deploy.sh       # Build, push, and deploy to Google Cloud Run
sql/
  001_users.sql  # Reference copy of the users schema (see below)
```

## Environment Variables

Copy `.env.example` → `.env`. All values validated by Zod at startup.

```
DATABASE_HOST, DATABASE_PORT, DATABASE_USER, DATABASE_PASSWORD, DATABASE_NAME
PORT            # default 3000
HOST            # default 0.0.0.0
ROW_LIMIT       # max rows per query, default 100, bounded 1–10000
```

There is no shared auth secret in env anymore — see **Auth & Users** below.

## Auth & Users

- No shared `AUTH_TOKEN`. Every `/mcp` request must carry `Authorization: Bearer <api-key>` where `<api-key>` belongs to a row in the `users` table (see `src/users.ts`, schema in `sql/001_users.sql`).
- Keys are generated by `manage-users -- add <username>` and shown exactly once — only a SHA-256 hash is stored (`api_key_hash`), never the raw key.
- Each user has a `role` of `user` or `admin`; `admin` is currently just a stored value — no query enforcement reads it yet (see Known Issues below).
- `add` is idempotent: re-running it for an existing username rotates their key and reactivates them. `rotate` requires the user to already exist.
- The auth middleware resolves the caller to a `McpUser` (`c.get("mcpUser")` — `username`, `role`, etc.) but nothing downstream (tool handlers) uses it yet.
- **Connecting from Claude**: this server is added as a custom connector (remote MCP, `Authentication: None`, then add a `Request headers` entry — header `Authorization`, value `Bearer <api-key>`). Each person adds their own connector instance with their own personal key. Rotating a key means removing and re-adding the connector — Claude doesn't allow editing auth on an existing custom connector.

## Key Architecture Decisions

- **Why Hono over Express**: `@hono/mcp` middleware prevents double-processing of requests and auto-detects request operation type. (Switched in commit `26388c6`.)
- **Sessions**: in-memory `Map<string, Transport>` keyed by UUID. No persistence — sessions are per-server-process.
- **Read-only enforcement**: all queries run inside `BEGIN READ ONLY` transactions at the DB level, not just application logic.
- **LIMIT injection**: if a SELECT query has no LIMIT clause, one is automatically appended using `ROW_LIMIT`.
- **Single shared pool**: one `postgres.js` pool (max 10 conns) shared across all MCP sessions.
- **Per-user auth**: replaced the single shared `AUTH_TOKEN` with per-user hashed API keys in `users`, so each caller has a distinct, verifiable identity instead of one bearer secret everyone shares.

## Adding a New Tool

1. Add the tool definition to `src/tools/postgres.ts` — follow the existing pattern (`description`, `schema` as Zod object, `handler` returning `toText(...)`)
2. Register it in `src/mcp.ts` via `server.registerTool()`

## Testing Notes

- Smoke tests (`npm test`) hit a live server — make sure `npm run dev` or `npm start` is running first, and `.env` is configured.
- `claude-test.sh` temporarily registers the MCP server with the Claude CLI, runs a prompt with all `postgres-*` tools pre-approved, then auto-cleans up on exit.

## Database Access (Neon)

Neon has no built-in migration system — it's just Postgres. Schema changes are applied manually; there's no migration framework in this project (no Prisma/node-pg-migrate/Flyway). The `sql/` directory holds reference SQL (documentation of what schema should exist), and where possible the same statement is also run idempotently at app/CLI startup (e.g. `CREATE TABLE IF NOT EXISTS` in `ensureUsersTable()`, `src/users.ts`) so first-time setup needs no manual step. Anything beyond an additive `CREATE TABLE IF NOT EXISTS` (e.g. `ALTER TABLE`) has no auto-apply path — add a new file under `sql/` for reference, then run it by hand.

The Neon CLI (`neon`, authenticated as sambrappaport) is available in this environment and can run SQL directly against the database — use it to verify schema/data or apply manual changes without going through the app:

```bash
neon psql --project-id rough-haze-46193679 --pooled -- -c "SELECT * FROM users;"
```

- Project: `shared-with-friends` (`rough-haze-46193679`), org `org-small-silence-75760406`
- Single branch: `production` (`br-lingering-resonance-a4jyebw6`) — no dev/staging branch exists yet, so any SQL run here hits the same database the running app uses

## Deployment

**Database**: NeonDB (serverless Postgres). Use their pooled connection string in `.env`. Keep postgres.js pool `max` at 10 or lower.

**Server**: Google Cloud Run. `scripts/deploy.sh` handles build, push to Artifact Registry, and deploy. Fill in `PROJECT_ID` at the top of that script before first use.
- Multi-stage Dockerfile: builder compiles TS, production stage runs only `dist/` + prod deps
- Cloud Run injects `PORT=8080`; app reads it automatically via `config.ts`
- `--max-instances 1` is required — sessions are in-memory, multiple instances would break the MCP session model

```bash
bash scripts/deploy.sh
```

## Current Work

Just landed per-user API key auth (`users` table + `manage-users` CLI, see **Auth & Users**), replacing the single shared `AUTH_TOKEN`.

Deferred / not yet built:
- Row-level scoping — filtering `query`/`list_tables`/etc. results so non-admin users only see rows tied to their own `username`. Requires deciding which column on business tables represents ownership; explicitly punted until needed. `role` is stored per user but nothing enforces it yet.
- Some tables may eventually be marked public/readable by everyone regardless of user, bypassing per-user scoping — not designed yet.
